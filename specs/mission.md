# ThinkXecAI Mission

## Purpose

ThinkXecAI is an AI agent assistant system. The system must support multi-step agent reasoning, explicit tool execution, knowledge-base retrieval, chat history persistence, and real-time execution feedback.

## Constitution Rules

- Treat the files in `specs/` as the project-level source of truth.
- Preserve the technical architecture and behavior unless a future spec explicitly changes them.
- The product and user-facing identity is `ThinkXecAI`; do not change the technology choices, data model, API behavior, runtime flow, or feature scope.
- Implement features in small, verifiable steps and update the specs before changing product direction.
- Do not replace Spring Boot, Spring AI, MyBatis, PostgreSQL, pgvector, React, Vite, Ant Design, SSE, or the local Ollama embedding flow.

## Product Goals

- Provide a configurable AI agent that can answer user requests through a Think-Execute loop.
- Let users create agents with a name, description, system prompt, model, allowed tools, allowed knowledge bases, and chat options.
- Let users create and manage chat sessions for agents.
- Persist all user, assistant, and tool messages in PostgreSQL.
- Let users create knowledge bases, upload Markdown documents, parse them into sections, embed them, and retrieve relevant chunks with pgvector.
- Let the agent call fixed tools and configured optional tools through Spring AI tool callbacks.
- Stream generated assistant and tool messages to the frontend with Server-Sent Events.
- Provide a usable React interface for agent management, knowledge-base management, chat history, and live agent output.

## Feature Scope

ThinkXecAI must include these features:

- Agent CRUD: list, create, update, and delete agents.
- Agent configuration: `name`, `description`, `systemPrompt`, `model`, `allowedTools`, `allowedKbs`, and `chatOptions`.
- Chat session CRUD: list all sessions, get one session, list by agent, create, update, and delete.
- Chat message CRUD: list by session, create, update, and delete.
- User message trigger: creating a user chat message starts an asynchronous agent run.
- Agent runtime: restore recent memory, apply system prompt, call the selected chat model, detect tool calls, execute tools manually, persist generated messages, and stop after completion or a maximum of 20 steps.
- Tool system: fixed tools are always enabled; optional tools are selected per agent.
- Fixed tools: knowledge retrieval, terminate, city, date, and weather.
- Optional tools: PostgreSQL read-only query tool and QQ email sending tool.
- Sample data: include a seeded e-commerce database schema so the read-only database query tool has realistic data to inspect.
- Knowledge-base CRUD: list, create, update, and delete knowledge bases.
- Document management: list all documents, list by knowledge base, create document records, upload files, update, and delete.
- Markdown ingestion: parse top-level Markdown sections by heading, preserve table Markdown when possible, and create one vector chunk per section.
- RAG retrieval: embed a query with local `bge-m3`, search `chunk_bge_m3` by vector distance, and return the top 3 chunk contents.
- SSE: one connection per chat session, initial `init` event, JSON `message` events, and cleanup on completion, timeout, or error.
- Frontend: sidebar layout, agent tabs, knowledge-base tabs, chat view, chat input, chat history, modals for adding agents and knowledge bases, API hooks, and SSE event handling.

## Non-Goals

- Do not add authentication, authorization, teams, billing, or tenant isolation.
- Do not add WebSocket transport.
- Do not replace PostgreSQL with another database.
- Do not replace MyBatis with JPA or another ORM.
- Do not replace local Ollama embeddings with hosted embeddings.
- Do not add new document formats beyond the Markdown processing behavior defined in this spec.
- Do not add streaming token-by-token model output; only persisted assistant and tool messages are pushed over SSE.
- Do not add a new UI design system.

## Success Criteria

- A programmer can build the project from an empty repository using only these specs and reach the specified feature set.
- All REST endpoints return the same response envelope shape: `{ "code": 200, "message": "...", "data": ... }`.
- The agent loop persists and streams assistant and tool messages exactly as defined by this constitution.
- Markdown upload produces `chunk_bge_m3` rows with `VECTOR(1024)` embeddings generated by local `bge-m3`.
- The React app can create an agent, create a chat session, send a user message, receive SSE-generated messages, manage knowledge bases, and upload Markdown documents.
